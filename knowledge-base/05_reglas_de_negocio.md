# Reglas de Negocio

A continuación se listan las 20 reglas de negocio codificadas del sistema, su garante esperado y el comportamiento ante incumplimiento:

| Código | Enunciado de la Regla | Garante Esperado | Comportamiento / Error |
| :--- | :--- | :--- | :--- |
| **RN-01** | El correo de un usuario y el documento de un cliente son únicos. La patente de un vehículo y el código de un repuesto son únicos entre los que no están dados de baja. | UNIQUE e índices únicos parciales en la base (`WHERE borrado_en IS NULL`). | HTTP 409 con mensaje propio (sin exponer trazas de BD). |
| **RN-02** | El auto-registro crea el usuario, su rol `CLIENTE` y su ficha de cliente: o quedan las tres filas, o ninguna. Si el documento ya es de un cliente del taller, el registro da 409 y no se apropia de esa ficha. | Un solo Unit of Work atómico. | HTTP 409 si el documento ya existe o el email choca; rollback total. |
| **RN-03** | Un usuario tiene a lo sumo una asignación abierta por rol. | Índice único parcial `(usuario_id, rol) WHERE revocada_en IS NULL`. | HTTP 409 si ya posee el rol activo. |
| **RN-04** | Los permisos se deciden con los roles vigentes en la base, en cada petición. Los roles que trae el token son meramente informativos. | Dependencia FastAPI que consulta la tabla `asignacion_rol`. | HTTP 403 inmediato tras revocación, incluso con token válido. |
| **RN-05** | Un administrador no puede revocarse su propio rol `ADMIN`, y el sistema nunca puede quedar sin administradores vigentes. | Comprobación en capa Service. | HTTP 409 si intenta auto-revocarse o revocar al último admin. |
| **RN-06** | Mientras un usuario tenga el cambio de contraseña pendiente (`debe_cambiar_password=True`), sólo puede usar las rutas de salud (`/health/*`), `/auth/*` y las de `GET`. | Middleware / Dependencia en grupo de rutas protegidas de FastAPI. | HTTP 403 para cualquier ruta de mutación fuera de `/auth`. |
| **RN-07** | Al cambiar la contraseña, las sesiones emitidas antes dejan de valer, aunque sean del mismo segundo que el cambio; la que devuelve el propio cambio, no. | Comparación de `iat` (timestamp con microsegundos/float) contra `password_cambiada_en`, sin truncar a segundos. | HTTP 401 en sesiones previas; la nueva sesión funciona. |
| **RN-08** | Después de 5 intentos fallidos con el mismo correo desde la misma IP en 60 segundos, el login responde 429 sin verificar la contraseña. Un login correcto reinicia la cuenta. | Conteo en `intento_acceso` en sesión/transacción independiente. | HTTP 429 con cabecera `Retry-After`. |
| **RN-09** | El login responde lo mismo, y tarda lo mismo, exista o no el correo (protección contra enumeración de usuarios). | Mismo mensaje `"Credenciales inválidas"`; verificación contra hash ficticio generado en Lifespan. | HTTP 401 tiempo uniforme (~300ms de bcrypt). |
| **RN-10** | Una orden nace `PENDIENTE` con al menos un ítem y sin repuestos repetidos. El precio de cada ítem se copia del repuesto, y el total lo calcula el servidor. | DTO de entrada con Pydantic y Service. Precio y total nunca viajan en el payload. | HTTP 422 si items vacíos o repetidos; precio y total blindados. |
| **RN-11** | Transiciones permitidas: `PENDIENTE -> EN_REPARACION` (mecánico queda asignado), `EN_REPARACION -> TERMINADA` (mecánico asignado o ADMIN), `PENDIENTE -> CANCELADA`. | Lógica en capa Service y verificación con catálogo `estado_orden`. | HTTP 409 si el estado actual no permite la transición. |
| **RN-12** | Cancelan una orden la recepción, el administrador o el dueño del vehículo. El permiso se evalúa antes que el estado. | Capa Service evalúa pertenencia/rol antes de chequear el estado. | HTTP 403 antes que HTTP 409. |
| **RN-13** | Terminar una orden descuenta el stock de cada ítem, deja un movimiento por cada salida y una línea de historial. Si un repuesto no alcanza, no queda ninguna de esas escrituras. | Un solo Unit of Work atómico. | HTTP 409 si stock insuficiente; rollback completo. |
| **RN-14** | El stock de un repuesto sólo cambia a través de movimientos: el alta con stock inicial, la reposición y la terminación de órdenes. No se edita por PATCH. | Punto único de mutación de stock en el repositorio/servicio; schema prohíbe campo stock. | HTTP 422 si se envía `stock` en PATCH (`extra="forbid"`). |
| **RN-15** | `historial_estado_orden`, `movimiento_stock` e `historial_precio_repuesto` son de sólo agregado: nadie puede modificar ni borrar sus filas. | Disparadores (Triggers) PL/pgSQL instalados en la 2da migración Alembic. | PostgreSQL Exception traducida a rechazo/error controlado. |
| **RN-16** | Un vehículo o un repuesto dado de baja deja de aparecer y no se puede usar en órdenes nuevas, pero sus datos se conservan. Un vehículo con órdenes abiertas (`es_final=False`) no se da de baja. | Soft delete (`borrado_en`); validación de órdenes activas en Service. | HTTP 409 si el vehículo tiene órdenes no finales; borrado lógico exitoso da 204. |
| **RN-17** | Lo propio sólo pide estar autenticado: un cliente ve sus vehículos (`/mis-vehiculos`) y las órdenes de sus vehículos (`/mis-ordenes`), y ninguna otra. | Filtrado por `cliente_id` del usuario autenticado; validación de dueño en `/ordenes/{id}`. | HTTP 403 si intenta acceder a un vehículo u orden ajena. |
| **RN-18** | Ningún error devuelve al cliente texto interno de la base de datos (sección 4.13). Ninguna entrada inválida termina en un 500. | Exception handler global que captura `IntegrityError` y valida Pydantic. | Códigos 400/404/409/422 limpios con mensaje de negocio. |
| **RN-19** | Los estados posibles de una orden son las filas del catálogo `estado_orden`. El catálogo se consulta desde la API y no se edita desde ella. Si está vacío, crear una orden responde 409 con mensaje propio. | Clave foránea a catálogo; repositorio de sólo lectura; chequeo previo al alta. | HTTP 409 si el catálogo no fue sembrado. |
| **RN-20** | Cada cambio del precio de un repuesto deja una línea en `historial_precio_repuesto`, en la misma transacción que el cambio. Un PATCH que no cambia el precio no deja línea. | Un solo Unit of Work; CHECK en BD `precio_nuevo <> precio_anterior`. | Registro atómico en historial; sin cambios si el precio es idéntico. |
